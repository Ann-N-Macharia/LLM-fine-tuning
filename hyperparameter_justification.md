# Hyperparameter Justification — `fine_tune.py`

QLoRA fine-tune of `meta-llama/Meta-Llama-3.1-8B-Instruct` on the Kenya Legal Aid dataset (~80 train / ~10 val examples, short Q&A pairs). Values below are read directly from the current `fine_tune.py` config block (lines 19–29, 39–44, 106–120).

> **Note before training:** `OUTPUT_DIR = "afyaplus-llama-adapter"` (line 15) is a leftover name from the healthcare (AfyaPlus) example domain — rename it to something like `"kenya-legal-aid-adapter"` before you run this, or your deliverable folder names won't match your chosen domain.

## LoRA (adapter) hyperparameters

| Hyperparameter | What it controls | High-value adjustment effect | Low-value adjustment effect | Justification for the value used |
|---|---|---|---|---|
| `LORA_R = 16` | Rank of the low-rank adapter matrices — how many trainable dimensions are inserted into each targeted weight matrix. Directly sets adapter capacity. | Higher rank (e.g. 32–64) increases trainable parameters and the adapter's capacity to learn complex patterns, but raises overfitting risk on a small dataset and increases VRAM/compute cost. | Lower rank (e.g. 4–8) trains faster and generalizes more conservatively, but may be too low-capacity to absorb the domain's legal vocabulary and citation patterns. | 16 is the standard mid-range default for QLoRA on 7–8B models and a single-domain, ~100-example dataset. It gives the adapter enough capacity to learn Kenya-specific legal phrasing and citation patterns without the parameter count needed to memorize (and overfit) such a small corpus. |
| `LORA_ALPHA = 32` | Scaling factor applied to the LoRA update (`alpha/r` scales how strongly the adapter output is added to the frozen base weights). | A higher alpha (relative to r) makes the adapter's influence on outputs stronger, which can speed up learning but risks destabilizing training or overpowering the base model's general knowledge. | A lower alpha mutes the adapter's effect, slowing adaptation and risking underfitting — the model stays closer to its untuned behaviour. | Set to `2 × r` (32 = 2 × 16), the widely-used QLoRA convention. This ratio has empirically produced stable training across model sizes and is the safest default absent a hyperparameter sweep, which this capstone's compute budget doesn't allow. |
| `LORA_DROPOUT = 0.05` | Dropout probability applied within the adapter layers during training — a regularizer. | Higher dropout (e.g. 0.1–0.2) regularizes more aggressively, reducing overfitting risk further but potentially slowing/limiting convergence on an already-small dataset. | Lower or zero dropout removes this regularization, raising overfitting risk given only ~80 training examples. | 0.05 is a light regularizer appropriate for a small, curated dataset — enough to discourage memorizing individual Q&A pairs verbatim without meaningfully slowing convergence over only 3 epochs. |
| `TARGET_MODULES = [q_proj, v_proj, k_proj, o_proj]` | Which weight matrices inside each transformer layer receive a LoRA adapter — here, all four attention projection matrices. | Adding more modules (e.g. `gate_proj`, `up_proj`, `down_proj` — the MLP block) increases trainable parameters and can improve adaptation quality, at higher VRAM and overfitting cost. | Targeting fewer modules (e.g. only `q_proj`/`v_proj`) reduces trainable parameters and cost, but limits how much of the model's behaviour can shift, potentially under-adapting to the domain. | Targeting the full attention block (not just Q/V) is a common QLoRA choice that captures more of how the model attends to context — relevant here since correctly identifying *which* Act/section applies to a scenario is fundamentally an attention/retrieval problem. MLP modules were left untouched to keep the trainable parameter count (and overfitting risk) low for this dataset size. |

## Quantization (QLoRA base model loading)

| Hyperparameter | What it controls | High-value adjustment effect | Low-value adjustment effect | Justification for the value used |
|---|---|---|---|---|
| `load_in_4bit=True`, `bnb_4bit_quant_type="nf4"` | Loads the frozen 8B base model in 4-bit NormalFloat precision instead of 16/32-bit, cutting memory footprint roughly 4x. | N/A (boolean/type choice, not a scalar to raise) — NF4 is already the higher-fidelity 4-bit option vs. plain FP4. | Using standard FP4 instead of NF4 would slightly reduce numerical fidelity to the original weight distribution. | This is what makes fine-tuning an 8B model feasible at all on a single rented GPU (Vast.ai). NF4 is specifically designed to match the roughly-normal distribution of pretrained transformer weights, minimizing quantization error compared to plain 4-bit formats. |
| `bnb_4bit_use_double_quant=True` | Quantizes the quantization constants themselves, saving a further ~0.4 bits/parameter. | N/A (boolean). | Disabling it uses slightly more VRAM with no accuracy benefit. | Free memory saving with negligible accuracy cost — no reason to disable it on a memory-constrained rented instance. |
| `bnb_4bit_compute_dtype=torch.bfloat16` | The precision used for the actual matrix-multiply compute during forward/backward passes (weights stay stored in 4-bit; compute happens in bf16). | N/A (dtype choice). | Using fp16 instead risks overflow/instability on some ops; using fp32 compute would be more stable but much slower and defeat the memory savings. | bf16 has the same exponent range as fp32 (avoiding fp16's overflow issues) while being much cheaper than fp32 compute — the standard choice for modern (Ampere+) GPU training. |

## Optimization / training loop

| Hyperparameter | What it controls | High-value adjustment effect | Low-value adjustment effect | Justification for the value used |
|---|---|---|---|---|
| `LEARNING_RATE = 2e-4` | Step size for the optimizer's weight updates. | A higher LR (e.g. 5e-4+) speeds up learning but risks loss spikes/divergence, especially with so few steps to recover from a bad update on a small dataset. | A lower LR (e.g. 5e-5) trains more stably but may not adapt meaningfully within only 3 epochs over ~80 examples. | 2e-4 is the standard QLoRA learning rate for adapter-only training (adapters can tolerate higher LRs than full fine-tuning since the base weights are frozen and can't be damaged). Combined with cosine decay and warmup, this balances meaningful adaptation against instability risk within a short run. |
| `BATCH_SIZE = 4` (per device) | Number of examples processed per forward/backward pass before an optimizer step (before grad accumulation). | A larger batch gives smoother gradient estimates and better GPU utilization, but requires more VRAM — likely to OOM on a V100. | A smaller batch (e.g. 1–2) fits easier in memory but produces noisier gradients. | Set to fit comfortably in a V100's 16GB VRAM budget alongside the 4-bit model and optimizer states; the comment in-file explicitly notes this should be raised to 8 on an H100, i.e. it's a hardware-fit choice, not a modeling one. |
| `GRAD_ACCUM = 4` | Number of forward/backward passes accumulated before each optimizer step; combined with batch size gives the *effective* batch size (4 × 4 = 16). | Higher accumulation increases the effective batch size (smoother gradients) without extra VRAM, at the cost of more time per optimizer step. | Lower accumulation makes each optimizer step happen sooner but with a smaller, noisier effective batch. | Effective batch size of 16 is a reasonable target for stable gradient estimates on a small dataset, achieved without needing the VRAM a true batch-of-16 forward pass would require. |
| `NUM_EPOCHS = 3` | How many full passes over the training set. | More epochs (5–10+) let the model see the data more times, but with only ~80 examples this sharply raises overfitting/memorization risk. | Fewer epochs (1–2) reduce overfitting risk but may leave the model under-adapted to the domain's tone and citation habits. | 3 epochs is a standard, conservative starting point for small instruction-tuning datasets — enough exposure to shift style and content grounding without many repeated passes over the same ~80 examples, which is exactly what the validation-loss curve (Deliverable 2's diagnosis) is used to confirm or correct. |
| `MAX_SEQ_LEN = 768` | Maximum token length per training sequence; longer examples are truncated. | A higher limit (e.g. 1024+) avoids ever truncating an example but increases memory/compute per step. | A lower limit (e.g. 512) trains faster and uses less memory, but leaves too little headroom once the system prompt is prepended to every example — SFTTrainer truncates from the end, which is exactly where the mandatory disclaimer sentence sits in every answer, risking silent loss of the safety disclaimer during training. | Originally 512, but checked against the actual worst case: system prompt (~180 tokens) + longest question (34 words) + longest answer (170 words) approaches ~460–470 tokens by even a conservative estimate, and the real LLaMA tokenizer typically runs higher than that estimate for capitalized Act names and legal terms. Raised to 768 for safe headroom at negligible extra compute cost, so no example — and critically, no disclaimer — is ever truncated. |
| `lr_scheduler_type="cosine"` | How the learning rate changes over the course of training after warmup. | N/A (scheduler shape choice, not a scalar). A more aggressive schedule (e.g. constant LR) risks late-training instability. | A linear or step decay would also work but cosine decays smoothly, avoiding sharp LR drops. | Cosine decay is the standard pairing with warmup for short fine-tuning runs — it lets the model make large updates early and fine, small updates as it approaches convergence near the end of the 3 epochs. |
| `warmup_ratio = 0.03` | Fraction of total steps spent linearly ramping the LR up from 0 to the target LR before decay begins. | A longer warmup (e.g. 0.1) is safer against early loss spikes but "wastes" more of a short run at a below-target LR. | No/very short warmup risks an unstable first few steps, since the optimizer's adaptive moment estimates haven't stabilized yet. | 3% is a light-touch warmup appropriate for a short run (few hundred total steps expected given the dataset size) — enough to avoid a first-step instability spike without eating meaningfully into the limited training budget. |
| `weight_decay = 0.001` | L2 regularization strength applied to weight updates. | Higher decay (e.g. 0.01–0.1) regularizes more strongly, reducing overfitting further but potentially slowing adaptation. | Lower/zero decay removes this regularizer, raising overfitting risk on the small dataset. | A light value appropriate for adapter-only training — the frozen base model already carries strong general-language regularization; only mild additional decay is needed on the small set of newly-trained adapter weights. |
| `bf16=True` | Whether the trainer runs in bfloat16 mixed precision. | N/A (boolean). | Running in fp32 would be far slower and use much more memory for no accuracy benefit on a compatible GPU. | Matches the `bnb_4bit_compute_dtype` choice above and is supported on the target hardware (V100/H100 class), giving faster training at negligible accuracy cost. |
| `optim="paged_adamw_8bit"` | Which optimizer is used, and how its state is stored. | N/A (optimizer choice). | A standard (non-paged, non-8bit) AdamW would keep full-precision optimizer state entirely in GPU memory, risking OOM on a memory-constrained rented instance. | 8-bit AdamW halves optimizer-state memory versus standard AdamW, and "paged" allows CUDA to spill state to CPU RAM under memory pressure rather than crashing — both directly address the VRAM constraints of a rented Vast.ai GPU. |

## Checkpointing and model selection

| Hyperparameter | What it controls | High-value adjustment effect | Low-value adjustment effect | Justification for the value used |
|---|---|---|---|---|
| `eval_steps = 10`, `save_steps = 10` | How often (in optimizer steps) the model is evaluated on the validation set and checkpointed. | Less frequent evaluation (e.g. every 50 steps) reduces overhead but gives a coarser view of the loss curve, potentially missing the exact point overfitting begins. | More frequent evaluation (e.g. every step) gives maximum visibility but adds significant overhead relative to a short run. | Given the dataset's small size, the total number of steps per epoch is low, so evaluating every 10 steps still yields enough points to plot a meaningful train/val loss curve (required for Deliverable 2's diagnosis) without dominating total run time. |
| `save_total_limit = 3` | Maximum number of checkpoints kept on disk at once (older ones deleted). | Keeping more checkpoints (e.g. 5–10) gives more rollback options but uses more disk space, a real constraint on rented instances. | Keeping fewer (e.g. 1) saves disk space but removes the ability to roll back to an earlier checkpoint if the best one turns out to be more than 1–2 saves back. | 3 balances disk usage against having enough recent checkpoints to recover the best one once `load_best_model_at_end` identifies it. |
| `load_best_model_at_end=True`, `metric_for_best_model="eval_loss"`, `greater_is_better=False` | Whether training ends by reloading the checkpoint with the lowest validation loss, rather than simply the last checkpoint. | N/A (boolean/selection policy). | Disabling this would keep whichever checkpoint happened to be last, even if validation loss had already started rising (overfitting) by that point. | Directly protects against shipping an overfit adapter — since validation loss is being monitored every 10 steps, this ensures the final saved adapter is the best-generalizing one seen during the run, not just the most-trained one. |

## Data pipeline

| Hyperparameter | What it controls | High-value adjustment effect | Low-value adjustment effect | Justification for the value used |
|---|---|---|---|---|
| `packing=False` | Whether multiple short training examples are concatenated into a single sequence to fill `MAX_SEQ_LEN`, vs. one example per sequence. | Enabling packing (`True`) improves GPU utilization by reducing padding waste, but risks the model learning spurious continuations across unrelated Q&A pairs packed into the same sequence. | N/A — this is already the safer (`False`) setting. | Kept off deliberately (per the in-file comment) so each training sequence corresponds to exactly one legal scenario — important for this domain, where blurring the boundary between two unrelated Q&A pairs could teach the model to answer one question using facts from an adjacent, unrelated one. |
